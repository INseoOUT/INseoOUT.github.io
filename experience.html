상황
서로 다른 방향을 향한 고정 카메라 두 대의 동기화된 영상을 하나의 광각 파노라마 영상으로 변환하는 데스크톱 소프트웨어를, 요구사항 정의부터 설계·구현까지 담당했습니다.
문제

세 가지 요구가 서로 충돌했습니다.

  • 시간적 안정성 — 프레임마다 정렬·이음매를 다시 계산하면 화면이 미세하게 떨립니다(플리커).
  • 속도 — 1080p 두 장을 4K로 합성하면서 실용적인 처리량이 필요했습니다.
  • 장시간 안정성 — 입력 길이와 무관하게 메모리가 한정되어야 했습니다.
선택
  • “한 번 계산하고 얼린다”를 설계 원칙으로 삼았습니다. 정렬·이음매·색보정을 대표 구간에서 한 번만 계산해 카메라 프로파일(JSON)에 동결하고, 렌더링은 그 고정 파라미터만 사용합니다. 프레임별 재계산은 플리커의 근원이라 판단해 고품질 모드에서만 선택적으로 열어 두었습니다.
  • 왜곡보정·투영·정렬 세 단계를 하나의 픽셀 단위 remap LUT로 합쳤습니다. 프레임당 remap 연산이 1회로 줄어 속도의 핵심 레버가 되었습니다. 이 불변식(렌더 잡당 LUT 빌드 1회)은 코드에 assert로 못박아 회귀를 막았습니다.
  • 스트리밍 파이프라인 — 전체 영상을 메모리에 올리지 않고 디코드 → 처리 → 인코드를 프레임 단위로 연결했습니다.
  • 기하 우선, ML은 보정만. 파노라마의 골격은 카메라 기하로 세우고 ML은 정밀 정렬·국소 워핑만 다듬도록 역할을 제한했습니다. ML이 픽셀을 생성하지 않게 한 것은 산업용 영상의 신뢰성 때문입니다.

직접 판단한 것

동기화 방식. 대상 영상에 유효 오디오가 없다는 사실을 확인하고, 표준적인 오디오 교차상관 동기화 대신 오버랩 영역의 프레임 간 모션 교차상관을 1급 경로로 채택했습니다. 오디오 방식은 나중에 끼워 넣을 수 있도록 인터페이스만 남겼습니다.

색보정 구조. 카메라별 스칼라 게인만으로는 오버랩을 맞출 수 없다는 점을 발견했습니다 — 센서마다 배율뿐 아니라 DC 오프셋이 다르기 때문입니다. 가중 곱합 구조는 가산 오프셋을 실을 수 없어, 오프셋을 동결된 캔버스 바이어스 이미지로 만들어 프레임당 1회 더하는 방식으로 풀었습니다. 렌더 엔진 변경을 두 줄로 최소화한 설계입니다.

한 일

죽은 코드 제거 — 컴파일은 되지만 런타임에 한 번도 인스턴스화되지 않는 탭 4개, 어디서도 참조되지 않는 벤더 라이브러리 트리(약 1,436개 파일), 도달 불가능한 레거시 블록(약 320줄)을 제거했습니다. 사전에 외부 참조가 없음을 전수 검색으로 확인하고 클린 리빌드로 검증했습니다.

HIGH 등급 결함원인과 해결
연결마다 SSL 객체 2개 누수 + Use-After-Free 가능성 수신 스레드의 무한 루프에 정지 플래그가 없어 연결 해제 후에도 소멸된 객체를 계속 참조 → atomic 정지 플래그 설정 후 스레드 join
연결 버튼을 누를 때마다 통신 객체 3종 누수 소멸자를 명시적으로 호출한 뒤 같은 포인터에 new — 소멸자는 돌지만 이전 힙 블록은 그대로 → delete로 전환
재연결마다 수신 스레드 블록·소켓 핸들 누수 소멸자가 실제 사용되는 소켓이 아니라 한 번도 할당되지 않는 다른 멤버를 닫고 있었음
매 아웃바운드 명령마다 메모리 누수 체크섬 버퍼의 new[]가 해제되지 않음
스택 오버플로우 가능 송신부가 크기 제한 없이 고정 1024바이트 스택 배열에 복사(페이로드는 2048자 초과 가능), 수신부는 큐에 쌓인 바이트 수를 목적지 버퍼 크기인 것처럼 전달 → 가변 버퍼화 + 실제 목적지 크기 전달
수정이 만든 2차 문제를 스스로 찾음

스택 오버플로우를 막으려 목적지 크기를 고정값으로 넘기면, 256바이트를 넘는 응답이 여러 메시지로 조용히 쪼개져 링버퍼에 남았다가 이후의 무관한 응답 앞에 붙을 수 있었습니다. 수정 직후 재검토에서 이 경로를 발견해, 실제 큐 길이를 크기로 지정하는 방식으로 원래 동작을 오버플로우 없이 복원했습니다.

부수 발견 — 수정 도중, 한글 주석의 인코딩이 저장 왕복 과정에서 깨져 컴파일러의 DBCS 렉서가 중괄호 매칭을 잘못 해석했고 그 아래 함수 전체의 빌드가 깨져 있던 것을 찾아 고쳤습니다.

통합 제어 아키텍처 설계와 드라이버 추상화 리팩터링

전 라운드 빌드 통과
C++아키텍처 설계점진적 리팩터링
상황
C++·Python 두 구현을 유지하면서 다른 카메라 모델도 교체 가능하게 지원해야 했는데, 카메라 프로토콜 지식이 UI 코드 곳곳에 흩어져 있어 확장이 어려웠습니다.
선택

7개 레이어·19개 모듈로 구성된 기술 중립적 통합 제어 아키텍처를 문서화해 양쪽 구현을 동시에 규율하도록 했습니다. 그다음 각 라운드가 “동작 변경 없음”을 목표로 하는 7단계 점진적 리팩터링으로 이행했습니다. 라운드마다 원본 로직과 손으로 대조하고 클린 빌드로 확인했습니다.

  • 기존 프로토콜 데이터 테이블을 드라이버 인터페이스 뒤로 감싸 와이어 프레임 조립과 체크섬을 단일 호출로 — 아무도 호출하지 않는 순수 추가로 시작
  • 탭이 부모 창에 메시지로 우회 전달하던 경로를 제거하고 드라이버 콜백으로 직접 전달
  • 이름이 제각각이던 전송 계층 3종(TCP·HTTPS·UART)을 공통 인터페이스로 통합 — 매번 새로 쓰던 3-way 분기를 단일화
  • 펌웨어 전송 경로와 프리셋 경로의 잔여 인라인 조립부까지 통합 → 체크섬 계산 로직이 앱 전체에서 한 곳
  • 가장 위험한 라운드로 로그 프레임 파싱을 드라이버로 이관 — 코드 작성 전 원본 로직을 독립적으로 재도출해 교차검증하고, 비대칭 바이트 순서와 중첩 로그 출력 순서 등 7가지 케이스를 라인 단위로 대조
통합 과정에서 발견한 실제 버그

Disconnect 버튼이 HTTPS만 정리하고 TCP·UART 세션은 살려 두고 있어, “연결 해제됨” 로그가 두 전송에 대해서는 거짓이었습니다. 리셋 블록을 공유 함수로 추출해 Disconnect에서도 호출하도록 고쳤습니다 — 해당 라운드의 유일한 의도적 동작 변경입니다.

의도적으로 남긴 것. 기존의 비대칭 두 가지(HTTPS 실패 시 SSL 복구 로직, UART의 “포인터 null 아님” 체크가 실제 “연결됨” 체크로 좁혀지는 것)는 동작 변경 위험 때문에 보존하고 문서에 남겼습니다.

선택

동작 무변경을 눈으로 확인하는 대신 통과해야 할 게이트로 만들었습니다.

  • 소스 호환 게이트 — 같은 헤더가 C++98·11·17 세 표준에서 모두 컴파일되는지 자동 검증. 하나라도 깨지면 이식분을 받지 않습니다.
  • vtable/ABI 대조 게이트 — 이식 전후의 가상 함수 배치를 대조해 기존 바이너리 소비자가 깨지지 않음을 확인.
  • 출력 회귀시험 고정 — 이식 과정에서 드러난 컬러맵 불일치를 회귀시험으로 고정해 재발을 막았습니다.
  • Boost 의존을 C++11 표준 라이브러리로 치환하고, 툴셋·SDK를 현행 버전으로 올렸습니다. 인코딩 혼용과 절대경로 하드코딩도 함께 제거했습니다.

한 일

만들기 전에 확인한 것부터 했습니다.

  • “신규 개발인가”부터 확인. 제안서는 “현재 육안 검사”를 전제했지만, 코드베이스 전수 검색 결과 통계 임계값 판정·국소 비교 판정·클러스터링 등급 판정이 세 갈래로 이미 흩어져 존재했습니다. 이 확인이 없었으면 이미 있는 것을 모르고 처음부터 다시 만드는 제안이 될 뻔했습니다.
  • 알고리즘의 대전제를 코드로 검증. 검출 로직 전체가 “보정이 꺼진 raw 프레임”을 전제하는데, 보정된 출력에는 불량 화소가 이미 지워져 있어 전제가 틀리면 알고리즘 자체가 무의미해집니다. SDK 헤더를 직접 확인해 raw 접근 함수의 존재를 확인했고, 일부 인터페이스 경로는 별도 확인이 필요하다는 한계도 함께 남겼습니다.
  • 기존 방식 대비 개선 근거를 항목별로 대조. 평균 대신 중앙값을 쓰면 타일 안에 불량 화소가 섞여도 견디고, 전역 고정 임계값 대신 MAD 기반 적응형 임계값을 쓰면 지역 잡음 수준을 매 윈도우마다 다시 추정할 수 있으며, 큰 비중첩 타일 대신 슬라이딩 윈도우를 쓰면 경계 블록 아티팩트가 사라집니다. 단일 프레임 검사만으로는 단발성 노이즈와 진짜 불량 화소를 구분할 수 없어 시간축 분산 체크도 추가했습니다.
  • 자기 알고리즘의 맹점을 스스로 짚었습니다. 국소 비교는 “주변은 정상”을 전제하므로 행·열 전체나 블록 단위 결함에서는 주변 중앙값 자체가 이미 죽은 값이라 검출되지 않습니다. 절대 기준값 비교를 별도 경로로 병행해 두 검출맵을 합집합으로 합치도록 설계했습니다.

“이미 다 있다”도 “완전 신규다”도 아닌 실제 상태를 규명하고, 기존 경로를 버리는 대신 고도화 + 독립 조건 추가로 확장하는 방향으로 정리했습니다.

일하는 방식

위 사례들에서
실제로 지킨 순서

  1. 검증 장치를 먼저 만든다

    합성 ground-truth 생성기와 골든 테스트를 코드보다 먼저 둡니다. 불변식은 assert로 못박습니다 — 렌더 잡당 LUT 빌드는 1회. 이후 결과물은 이 게이트를 통과하는지로 판정합니다.

  2. 동작 무변경을 기본 게이트로 둔다

    리팩터는 라운드마다 “바이트 동일”을 목표로 하고, 의도적 동작 변경은 라운드당 1건만 허용하며 반드시 명시합니다. 이식에서는 소스 호환·ABI 대조를 자동 게이트로 만들었습니다.

  3. 순수 추가로 시작한다

    새 추상화는 아무도 호출하지 않는 상태로 먼저 넣고, 배선은 다음 라운드에서 합니다. 되돌릴 수 있는 크기로 자릅니다.

  4. 다관점으로 훑고, 반드시 반증한다

    여러 관점으로 코드를 훑어 나온 지적을 그대로 믿지 않습니다. 반증 단계와 직접 재현을 통과한 것만 고칩니다 — 보고된 12건 중 6건은 통과하지 못했고, 기각한 2건은 소스에 근거가 적힌 의도된 설계였습니다.

  5. 전제를 코드로 확인한다

    제안서·문서의 전제를 그대로 받지 않고 코드베이스와 SDK 헤더로 직접 확인합니다. 확인하지 못한 경로는 한계로 적어 둡니다.

  6. 측정으로 레버를 고른다

    느리다고 바로 GPU를 붙이지 않습니다. CPU 스레딩의 천장을 먼저 측정해 병목이 remap 연산임을 확인한 뒤에 CUDA로 갔습니다. 영상 품질도 눈이 아니라 PSNR/SSIM으로 골랐습니다.

  7. 내가 만든 구멍은 내가 만든 구멍이라고 적는다

    수정이 만든 2차 문제, 검증하지 못한 경로, 의도적으로 남긴 비대칭 — 전부 문서와 커밋 메시지에 명시합니다. 상태를 정확히 아는 것이 빠른 것보다 중요합니다.
